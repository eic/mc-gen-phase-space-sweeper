# mc-gen-phase-space-sweeper

The stack that produces the ePIC generators-vs-η phase-space table: which detector
regions each generator's particles reach. Everything in this directory is
either an input pin, sweep code, sweep output, or the table built from it.

The table is pinned to **the EVGEN files a given production campaign actually
consumed**. The campaign is a parameter, `C` below, such as `26.07`, `26.04.1` or
`25.12.0`: any name the PCS catalog API knows. Each campaign keeps its own pins, sweep
outputs and table, so several can sit side by side. The committed one is 26.07.
Decisions and results are in `NOTES.md`.

## Layout

| Path | What | Committed |
|---|---|---|
| `pins/C/catalog.json` | Snapshot of the PCS campaign catalog | yes |
| `pins/C/evgen_inputs.json` | **Lock file**: every EVGEN file that fed a RECO/FULL output of campaign C, with its Rucio adler32, size and events | yes |
| `sweep/pin_inputs.py` | catalog + Rucio → lock file | yes |
| `sweep/resolve.py` | lock file → `run/C/manifest.json`, `run/C/chunks.txt`, `run/C/in/` (3 files per EVGEN dataset) | yes |
| `sweep/reproduce.py` | reruns resolve, sweep and table from the lock and checks every committed output byte for byte | yes |
| `sweep/check_pins.py` | checks that the chosen files still match the lock (size, and mtime where there's no checksum) | yes |
| `sweep/sweep.sub`, `sweep/run.sh` | HTCondor: one job per chunk, in `eic_xl:26.10-stable` (image digest checked) | yes |
| `sweep/phase_space.py` | maps each file's particles onto ePIC regions → `run/C/out/cNNNN.json` | yes |
| `sweep/markers.py` | `run/C/out/` → `results/C/latest_markers.json` (latest generator version per configuration) | yes |
| `table/spec.py`, `table/make_table.py` | table layout and wording (shared by all campaigns) → `table/C/generators_eta.{tex,pdf,png}` + provenance | yes |
| `run/C/manifest.json`, `run/C/chunks.txt`, `run/C/out/` | sweep inputs and outputs, so the table rebuilds without rerunning jobs | yes |
| `run/C/in/`, `run/C/log/` | regenerated by `resolve.py` / written by jobs | no |

## Rebuild the table from committed outputs

    python3 table/make_table.py 26.07 --check   # fails with a diff if the committed .tex is stale
    python3 table/make_table.py 26.07           # rewrites table/26.07/generators_eta.{tex,provenance.txt,pdf,png}

Host `python3` is enough (no ROOT or Rucio).

## Check reproducibility end to end

    python3 sweep/reproduce.py 26.07 --jobs 4   # about 6 min on 4 cores

This needs singularity, /cvmfs and xrootd access to dtn2304. It reruns three steps, and each must match what is committed byte for byte:
1. `resolve.py` from the lock;
2. every sweep chunk, into a scratch directory;
3. the markers and the table: `.tex`, provenance, `.pdf` and `.png`.

The PDF and PNG are built without timestamps or random IDs, so the images are byte-reproducible too. Nothing in the committed tree is modified.

The lock file itself is the pin and isn't regenerated by this check. Re-pinning queries the live catalog and Rucio, which keep changing while a campaign is still producing, so it's an update, not a reproduction.

## Rerun everything from scratch

Steps 1 and 3 need Rucio/xrootd, so run them in eic-shell. The default
read-only config (account `eicread`) is enough:

    C=26.07
    ES=/path/to/eic-shell        # your eic-shell launcher
    RUCIO_ENV='unset BEARER_TOKEN BEARER_TOKEN_FILE RUCIO_CONFIG'

1. **Pin** (about 2 min). Skip this step to reuse the committed lock file.

       printf '%s\n' "$RUCIO_ENV; cd $PWD; python3 sweep/pin_inputs.py $C" | $ES

   - This refetches the catalog. To rebuild from the committed snapshot instead, add `--catalog pins/$C/catalog.json`.
   - The script prints `unresolved entries 0`. A non-zero count goes into the lock's `unresolved` list.
   - `git diff pins/` shows what changed in the campaign.

2. **Select files.**

       python3 sweep/resolve.py $C

3. **Verify pins.** Every chosen file must still match the lock.

       printf '%s\n' "cd $PWD; python3 sweep/check_pins.py $C" | $ES

4. **Sweep** (for 26.07: 54 jobs, each about 30 s of reading).

       mkdir -p run/$C/out run/$C/log && condor_submit CAMPAIGN=$C sweep/sweep.sub

   Submit from the repo root, because `sweep.sub` takes the repo path from `$PWD`. When the jobs finish, every `run/$C/log/*.pyerr` should contain only `ok` lines:

       grep -L '^ok' run/$C/log/*.pyerr; grep -h FAIL run/$C/log/*.pyerr

   To rerun failed chunks, put their files into `run/$C/in/r_cNNNN.txt` and run `sweep/run.sh $C r_cNNNN $PWD`. `markers.py` reads `run/$C/out/r_*.json` after the originals, so the reruns take precedence.

5. **Table.**

       python3 table/make_table.py $C

   Rows of `table/spec.py` that have no data in campaign C are dropped and listed in the provenance file. A sweep row that `spec.py` doesn't place stops the build, so nothing disappears silently.

## What "used in campaign C" means

`pin_inputs.py` takes every sample in campaign C's catalog with status `submitted` or
`past_output` that isn't a particle gun and has a RECO or FULL output dataset. It
then lists each output file in Rucio and maps it back to its parent EVGEN file. Output names are the EVGEN stem plus numeric fields, for example
`<stem>.0083.eicrecon.edm4eic.root`, `<stem>.6316953.0001...` or `<stem>.0408.p6321667...`. tryN and
`Bkg_*` mixing prefixes are stripped. Consequences:

- Only files that produced at least one output are pinned. A dataset with 50 EVGEN files of which the campaign used one pins that one file.
- Datasets that the campaign didn't run aren't in its table. This holds even when a newer generator version exists on disk.
- In 26.07, 77 of the 204 EVGEN directories were never registered in Rucio; they come from older, pre-PanDA submissions. For those, the lock records the size and mtime from an `xrdfs ls -l` of EIC-XRD, and `adler32` is null. `check_pins.py` checks both values.
